# ValuationAgent 系统验收与改进建议

验收日期：2026-09-25。环境：用户现有 `economic_agent`，本地单进程服务，独立验收数据目录 `var/acceptance-20260925`。

## 验收结论

核心计算、任务版本、工具记录和报告输出具备可演示基础；本次可靠性验收仍有重要缺口，不建议直接定性为“高准确、高容错、可放心交付”。重点问题是财务字段与证据的语义对应、刷新后的任务恢复、公式工作簿解析性能和长会话传输量。

以下明确区分“已复现”“代码确认”和“产品建议”。本轮为验收，没有修改业务实现或 Tushare 模块。

## 已通过的验证与范围

- 后端完整回归：192 passed，1 个第三方依赖弃用警告。
- 前端领域测试：8/8；组件检查：7/7；代码检查通过。
- 真实本地接口联调：任务创建、对话、WACC 重算、旧版本保留、工具缓存、事件流、结果组件渲染通过。
- JSON、XLSX、PDF 导出接口均成功返回；本轮未重新进行 PDF 逐页视觉验收。
- 浏览器实际操作覆盖新研究、未连接模型引导、历史估值、结果图表、草稿刷新、执行中重新打开研究；检查桌面布局及 390 × 844 手机布局，观察到的浏览器控制台没有错误。
- 新增四类故意错配的取证样本、公式工作簿规模测试、完整会话响应规模测试及八请求并发测试。
- 本轮未重新调用真实 LLM / Tavily，不将本地演示和模拟故障测试当作完整真实企业联网估值验收。此前联网验证也不能替代多公司、多年财务的独立金标准对账。

## 优先修复项

### A1 · P1：错误年份、单位、口径、公司仍能成为“无警告”候选【已复现】

输入合成原文：甲公司2024年合并报表，单位万元；2024年营业收入1000，2023年900。分别故意提出以下错误候选：

| 错配 | 系统接受的候选 | 结果 |
| --- | --- | --- |
| 年份 | 把2023年的900标成2024年 | 无警告，能确认 |
| 单位 | 把1000万元标成1000亿元 | 无警告，能确认；归一值放大10000倍 |
| 口径 | 原文改成母公司报表，仍标为合并报表 | 无警告，能确认 |
| 公司 | 研究对象为乙公司，引用甲公司报表 | 无警告，能确认 |

复现到候选确认层，不意味着每个错误样本都已产生最终估值。它证明了“无警告”的判定不足以支撑用户直接批量确认。

原因：[research.py](../src/valuationagent/application/research.py) 的 `_facts` 检查连续引用和数值出现，但年份、单位、主体、口径主要采纳模型填写内容。后续财务勾稽不能保证发现同比例错单位或拿错公司等错误。

建议：把主体、报表口径、年度列、单位表头、数值单元格绑定为同一条证据；明示冲突必须阻断；无法确定的字段降低置信度并给出具体核对点。加入跨表/跨来源一致性检查和单位数量级检查。

验收要求：上述四类错配均不能无警告批量确认；正确样本不被误阻断。

### A2 · P1：执行中刷新页面后失去持续进度更新【已复现】

提交3份合成工作簿，在后台解析期间重新打开研究。页面停在 `v2 / 1份资料`，输入框可用且没有执行中提示。后台33.67秒后已完成，实际为 `v5 / 3份资料`；页面仍保持旧内容，再次手动刷新才更新。

原因：`ResearchDesk.jsx` 的900毫秒轮询仅在本次 `send()` 调用的生命周期内存在；重新挂载只读取一次快照。`busy` 是本地状态，服务端快照没有可用于恢复订阅的运行状态。

建议：把运行状态、当前步骤、任务标识放进服务端权威状态；页面重入后自动重新订阅，完成后再停止。加入“停止当前执行 / 稍后继续”、请求幂等标识，以及刷新后的完成通知。

验收要求：任务执行中刷新、关页再开、短时断网后，均能继续收到进度和最终结果；重复发送不重复创建同一动作。

### A3 · P1：带公式 Excel 解析出现明显的非线性变慢【已复现】

同一测试结构，每行一个公式；公式没有缓存值，系统仅读取公式及缓存，不执行计算。

| 表格 | 文件大小约 | 解析耗时 |
| --- | ---: | ---: |
| 800行纯数值 | 16.5 KB | 0.039秒 |
| 100行含公式 | 6.4 KB | 0.201秒 |
| 400行含公式 | 11.0 KB | 3.428秒 |
| 800行含公式 | 17.1 KB | 12.521秒 |

原因：[documents.py](../src/valuationagent/core/documents.py) 在遍历公式表时，对只读缓存工作表逐单元格使用 `cached_sheet[cell.coordinate]`，反复从前部解析。行数翻倍时耗时接近四倍。

建议：公式视图和缓存视图按行同步迭代，一次扫描完成；文档解析后台化，并显示文件级进度。缓存键使用文件哈希、解析器版本和解析选项。

建议验收目标：同机800行该样本低于1秒；更大样本按接近线性增长。该目标尚未验证达成。

### A4 · P1：长研究会话重复传输全部工具输出【已复现】

合成每条工具事件约20 KB，模拟一次读取4段财务原文。以下为5次本地HTTP请求的中位数，不是生产SLA：

| 工具事件数 | 单次完整快照 | 中位耗时 |
| ---: | ---: | ---: |
| 25 | 0.52 MB | 32.24毫秒 |
| 250 | 5.14 MB | 158.64毫秒 |
| 1000 | 20.56 MB | 519.32毫秒 |

1000事件样本8个并发请求全部成功，但耗时达到1.49—3.84秒。前端执行中每900毫秒取一次完整快照，会反复发送旧记录；这还没有计入真实长对话的浏览器渲染开销。

原因：`ResearchService.snapshot()` 返回全部消息、全部事件及工具输出，前端每次重新归并渲染。现有增量事件接口未用于研究工作台这一轮询路径。

建议：首次加载精简快照，后续按事件序号增量读取；工具输入输出在展开时单独加载；消息和日志分页或虚拟列表；无变化时不重渲染。历史列表也只返回摘要，按需加载详情。

验收要求：长期会话单次更新量主要随新增内容变化，不随累计历史等比例增长。

## 功能、容错与可复现性

### B1 · P2：模型瞬时超时直接中断，任务缺少明确的停止与时间预算【部分已复现】

模拟第一次模型请求超时、第二次可成功：当前只尝试一次，返回 `LLM_TIMEOUT`。HTTP 429/502/503/504已有重试，但超时和连接中断未进入相同的恢复策略。研究工具循环最多20轮，缺少任务级时间/费用预算和明确停止入口。

建议：按故障类型处理，连接失败与可安全重试请求采用退避；超时可能已经产生供应商费用，重试需有上限并披露。加入总时间预算、步骤耗时、可取消执行；用户可看见“正在检索/读取/提取”，而不是只见转圈。

### B2 · P2：未实际验证的搜索连接被显示为“已就绪”【已复现】

在独立测试研究中填写明显无效的占位 Tavily Key，连接接口仍返回 `available: true`，页面据此显示已就绪。接口仅保存适配器，没有验证连接成功。

建议：区分“已配置”“已验证”“连接失败”；提供测试连接，失败时保留输入和当前研究状态。

### B3 · P2：按估值方法补资料的策略仍过于统一【代码确认】

`research_valuation.py` 对不同方法统一要求完整FCFF字段和连续4年历史；正式金融模型的历史最少年度检查也没有完全按方法拆开。用户只做P/E或P/S时，仍可能被D&A、CapEx、营运资金等不直接相关字段拦住。

非Tushare研究转正式请求时也未组装 `PeerCompany` 列表，搜索得到的同业资料缺少直接进入正式相对估值的完整通道。

建议：建立DCF、P/E、P/S、EV/EBITDA各自的最小输入集合和时点规则；增加结构化同业候选、样本筛选依据和确认界面。允许先产出已具备证据的方法，并清楚解释其他方法为何暂不可用。

### B4 · P2：证据元数据和复现包需要贯穿研究到报告【代码确认】

研究转正式估值时 `_evidence()` 主要保留文件名、文件ID、块ID和引文，没有完整映射原来的页码、单元格、披露日和URL；`FinancialSnapshot.published_at` 也没有在这一组装路径中填充。正式模型虽有时点规则，但不能依靠缺失的披露日执行完整检查。

API的正式JSON导出仅返回 `record.result`；网页JSON导出另行组合 `run/artifacts/events`，内容不一致。研究导出固定写 `financial_model_status=not_connected`，即使研究已有正式运行关联，状态仍可能失真。

建议：统一导出契约，提供完整复现包：原始文件及哈希、来源URL与披露日、确认记录、有效输入、参数快照、版本、工具轨迹和结果；提供离线复算入口。研究与正式估值通过同一个追溯标识串联。

### B5 · P2：资料入口能力不一致【代码确认】

后端已有TSV/HTML解析，但网页上传过滤仍只接收PDF、DOCX、XLSX、CSV、JSON、TXT、MD。旧XLS并没有完整解析支持，应统一明确要求转换。扫描PDF仍缺OCR；PDF读取上限为400页，超长年报后部内容可能不在当前可读范围。

建议：前后端共享能力清单；支持按页范围补读和按需求解析；增加带页码与识别置信度的OCR。对“已读范围”和“未读范围”清晰标注。

### B6 · P2：还需独立金融金标准验收【已知边界】

行业参数快照仍标注缺少观测起止期、分行业样本量、更新频率、责任人及置信区间；食品饮料/白酒采用已披露的低质量兜底行。代码测试通过不能替代参数依据和独立财务复核。

建议：选择至少5个行业的真实公司，冻结估值时点和披露材料，用独立人工工作簿逐项对照历史字段、EBIT/FCFF、净债务、股数、终值、相对估值和敏感性；包含亏损、负营运资金、重述和单位错配案例。记录偏差和原因，而非只检查“是否生成结果”。

## 页面观感与使用便利

现有深蓝导航、浅色工作区、青绿色操作和估值区间图有统一性，桌面布局完整，手机检查没有观察到页面级横向溢出。适合做信息层级与操作路径优化。

| 项目 | 观察与建议 |
| --- | --- |
| 第一屏目标 | 首页偏“资料整理”，缺少鲜明的“输入公司→形成估值报告”主路径。建议公司/估值日/目标集中在一个启动卡，提供示例估值预览。 |
| 模型设置 | 普通用户不应一开始理解协议、Base URL、Thinking。默认显示供应商、模型和密钥，高级选项折叠；任务目标与连接设置分开。 |
| 当前进度 | 显示“已找到几份年报/已核对几个年度/尚缺哪些关键字段”，每一步提供可操作下一步，标明正常处理中还是等待用户。 |
| 财务确认 | 改为按年度列的表格：字段、原值、单位、归一值、证据页码、状态；可逐项修正和查看对应原文。SHA、块ID和原始JSON放入详情。 |
| 结果页面 | 首屏优先显示估值区间、方法差异、关键假设和数据质量；对话栏可折叠，让结果与敏感性拥有更大面积。导出按钮可合并为菜单。 |
| 手机体验 | 390×844结果页的对话框距顶部约3152px，需滚动三屏以上；640px以下数据服务按钮被隐藏。建议底部“研究/结果/资料”导航或固定“问Agent”入口，并保留设置菜单入口。 |
| 草稿与历史 | 实测未发送草稿在刷新后丢失。建议按研究保存非敏感草稿；附件保存已上传ID和状态；同一研究多个估值版本分组，增加历史搜索、重命名、归档。 |
| 可读性 | 增大辅助文字和关键状态字号，减少低对比浅灰文字；进一步统一术语。英文页面仍混入中文估值结论和质量说明。 |

## 性能基线与后续优先级

轻量请求当前较快：健康检查中位2.63毫秒；两个演示任务列表19.45毫秒。小型演示报告XLSX/PDF导出约0.32秒。入口JS约476 KB，当前静态服务未返回压缩编码；可后续做压缩、缓存和按视图拆包，但优先级低于公式解析与完整历史反复传输。

建议顺序：

1. 修复A1取证错配，建立错误样本回归；补齐披露时点及来源元数据。
2. 修复A2刷新恢复，并增加可停止执行、步骤反馈和草稿恢复。
3. 修复A3公式表解析与A4长会话增量更新，形成稳定性能基线。
4. 按估值方法补资料、完成非Tushare同业资料到相对估值的提交路径。
5. 优化启动、确认表格、结果展示、移动端入口；最后统一离线复现包并做真实公司金标准验收。
